# 经验总结：自建 IPTV 直播源工具链

> 这份文档记录的是**踩过的坑**，不是功能介绍。
> 工具本身看代码就懂，但下面这些结论每一条都花了几小时实测才确认，
> 而且几乎全都**与直觉相反**——照直觉写出来的脚本会得到完全错误的结论。

## 0. 结论先行

| 问题 | 答案 |
| --- | --- |
| 央视官方直链还能用吗？ | **不能。** 六条路线全部实测封闭（见 §3） |
| 现有订阅为什么"能测出高速率却播不出画面"？ | **冻结快照**（见 §1），这是最大盲区 |
| 网关编号能不能按 `hls/N → CCTV-N` 套？ | **不能。** 至少三套体系，必须逐网关抓帧确认（见 §2） |
| 本机测速慢/超时，要不要删掉这条源？ | **不要。** 本机与盒子出网路由常相反（见 §4） |
| 稳定源到底在哪？ | 运营商 `newlive` 网关 + 多网关冗余，靠**逐条指纹判活**筛出来 |

## 1. 最大盲区：冻结快照（Frozen Snapshot）

### 现象

某些 CDN 上的 `live.m3u8`：

- 播放列表能拉到，HTTP 200
- 分片能拉到，单分片几百 KB
- **测速结果全场第一**：实测 CCTV-1 那条 `50.14 / 48.25 / 34.33 Mbps`
- 但播放器打开后**永远卡在第一帧**，进度条不动

### 根因

这是 CDN 上残留的**历史 HLS 对象**。分片文件还在、还能拉、还很快，
但播放列表本身是死的：

```
#EXT-X-MEDIA-SEQUENCE  →  永不增长
#EXT-X-PROGRAM-DATE-TIME →  停在旧日期（实测见过 2020-07-31 / 2023-09-11 / 2025-06 / 2026-10）
```

播放器按 `MEDIA-SEQUENCE` 往后取分片，序号不动 → 永远取同一段 → 卡第一帧。

### 为什么常规测速抓不到

常规测速只回答两个问题：「**能不能拉到分片**」「**多快**」。
冻结快照对这两个问题的答案都是最优的。
**它不是网络问题，是内容属性**——换任何网络、任何设备都放不出来。

### 正确判活方法

指纹 = `(EXT-X-MEDIA-SEQUENCE, 最后一个分片的 URI)`

```python
def fetch_pl(url, timeout=10):
    """取播放列表，返回 (指纹, 状态)。"""
    try:
        req = urllib.request.Request(url, headers={'User-Agent': UA})
        r = OP.open(req, timeout=timeout)
        body = r.read(60000).decode('utf-8', 'replace')
        code = r.getcode()
    except Exception as e:
        return None, 'ERR:' + str(e)[:50]
    if code != 200:
        return None, 'HTTP%d' % code
    if '#EXTM3U' not in body:
        return None, 'NOT_M3U8'
    m = re.search(r'#EXT-X-MEDIA-SEQUENCE:(\d+)', body)
    seq = m.group(1) if m else ''
    segs = [ln.strip() for ln in body.splitlines()
            if ln.strip() and not ln.startswith('#')]
    if not segs:
        return None, 'NO_SEG'
    return (seq, segs[-1]), 'OK'
```

间隔 N 秒（实测 12~14 秒足够，HLS 分片一般 4~6 秒）取两次，**指纹变了才是真直播**。

对应工具：`tools/audit_live.py`（批量审计）、`tools/fix_by_audit.py`（按审计结果清理）。

```bash
python tools/audit_live.py output/curated.txt --wait 14 --workers 24
python tools/fix_by_audit.py            # 只看报告
python tools/fix_by_audit.py --apply    # 真正写盘
```

## 2. 网关编号：至少三套体系，不可跨网关套用

`newlive` 系列网关的频道编号**没有统一规律**。同一条 `/newlive/live/hls/N/live.m3u8`，
在 A 网关是 CCTV-5，在 B 网关可能是 CCTV-6。

实测四台网关，三套体系：

| 网关 | 编号规则 | 关键差异 |
| --- | --- | --- |
| `183.250.156.180:9999` | **直编**，无 5+ | `16` = 404，央视只到 15 |
| `118.122.144.115:8888` | **直编**，有 5+ | `16` = CCTV-5+，`17` = CCTV-17 |
| `219.147.245.238:25480` | **顺移 +1** | `6` = 5+，`7~16` = CCTV-6~15，`17` = CCTV-17 |
| `120.40.39.246:352` | **顺移 +1** | CCTV-17 在 `18` |

卫视段同样错位，例如 `118` 的 `18四川 / 19湖南 / 20江苏 / 21浙江 / 22东方 / 23北京 / 25东南`，
`120` 的 `30青海 / 31安徽`。

### 教训

我一度按单一 `hls/N → CCTV-N` 假设批量重排，算出「CCTV-6~17 全线串台 24 条」，
**是重大误报**。逐网关抓帧后，实际只有 2 条真错位：

- `东南卫视@118 hls/20` → 实为**江苏卫视**
- `江苏卫视@120 hls/31` → 实为**安徽卫视**

正确做法：**任何编号推断都必须抓帧确认台标**，不要相信规律。

对应工具：

- `tools/grab_frames.py` / `grab_frames2.py` — 抓关键帧拼图看台标
- `tools/ts_sdt.py` — 从 TS 的 SDT 表直接读频道名（最可靠，优先用这个）
- `tools/num_map.py` — 主机「台号 → 频道」查表，避免硬套

拼图时**单格至少 640×360**。用 4×4 拼成 1950×1110（每格 480×270）时台标糊到读不出，白干一轮。

```bash
FF=/path/to/ffmpeg.exe
"$FF" -y -framerate 1 -start_number 1 -i tmp/wsseq/%02d.png \
  -vf "scale=640:360,tile=4x2:margin=6:padding=6" -frames:v 1 -update 1 tmp/grid.png
```

注意 `-update 1`：单帧输出必须加，否则文件不生成。

## 3. 官方直链：六条路线全部封闭（2026-11 实测）

目标原本是找"最稳定的官方源"。结论：**这条路走不通**，逐条记录如下，
省得下次再试一遍。

| # | 路线 | 结果 |
| --- | --- | --- |
| 1 | 央视频网页 API | `iretcode 32` / `10016` / OSS `NoSuchKey` |
| 2 | cKey 签名算法复现 | 算法对，但仍被拦（见下方细节） |
| 3 | 央视网 CNTV CDN | 变体播放列表全部 404 |
| 4 | 央视网老接口 `vdn.live.cntv.cn` | 存活但返 `{"ack":"no","tip_msg":"该视频不存在"}` |
| 5 | 浙江广电 `ali-m-l.cztv.com` | **冻结快照**（见 §1） |
| 6 | 浙江广电 `ali-xwl.cztv.com` | 只有浙江本地 10 台，**无央视** |
| 7 | 央视频TV APK 的 OTT 接口 | 需设备鉴权，无法离线复现 |
| 8 | ICNTV CDN | 生产域名全部 DNS 失效 |

### cKey 签名细节（供后人参考）

```
xu  = "|" + int32(fnv1a(wu)) + wu
cKey = "--01" + HEX( AES-128-CBC(key, iv, pkcs7(xu)) ).upper()
```

UA 段必须是**固定模板串**，不能用真实 UA：

```
mozilla/5.0 (iphone; cpu||Mozilla|Netscape|Win32|
```

用真实 UA 直接返回 `iretcode 32`。

### 央视频TV APK

`com.newtv.cboxtv` v7.2.0，minSdk 17，22 个 `armeabi` 32 位 so
（`libTPCore-tvideo.so` 10.7 MB 最大）。dex 里的关键端点：

```
api/getPlayingEPG/{channelId}
api2/live.do
api/getHttpVideoInfo.do
epgapitxy.cloud.ottcn.com
plyauthtxy.cloud.ottcn.com
dispatch.cloud.ottcn.com
```

32 位 ABI 意味着老设备（如斐讯 T1 / Android 7.1.2）理论上能装，
但接口要设备鉴权，抓包复现成本高于收益。**这条路建议放弃。**

## 4. 本机不可达 ≠ 源失效

### 现象

本机审计时，`119.125.131.239` 的 33 条线路**全部超时**。
脚本一度把这些判为"死链"并降权。

### 真相

- 本机出口：`61.184.164.166`（湖北孝感**电信**）
- 目标盒子：`111.46.161.239`（湖北孝感**移动**）

两个运营商之间的路由**经常相反**。手机侧实测同一批线路 `7~29 Mbps` 全部正常。

### 铁律

> **本机结果只能判活，不能排序，更不能作为降权依据。**

`fix_by_audit.py` 里因此写了这段注释，并把 `dead_hosts` 恒设为空集：

```python
# 注意：本机不可达**不能**作为降权依据。
# 本机出口是湖北孝感电信，目标盒子是湖北孝感移动，两边路由常相反。
# 实测 119.125.131.239（移动 IP）本机全超时，手机上 7~29 Mbps 全 OK。
# 所以这里只处理「冻结快照」——那是 CDN 内容属性，与网络无关，任何网络都放不出来。
dead_hosts = set()
```

### 后续反转（说明为什么"不删"是对的）

后来手机端重测，`119.125.131.239` 的央视段 + 卫视段**确实全部 0.00**，整机失效。
于是 33 条**沉底保留**（不删除）。

保留而不是删除，是因为：
1. 失效可能是临时的（维护、限流），删了就再也找不回来
2. 沉底不影响使用，删除是不可逆的

**排序降权 ≠ 删除。** 这是两件事。

## 5. 完整流水线

```
┌─────────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐
│ ① 找源       │ → │ ② 测速    │ → │ ③ 判活    │ → │ ④ 合并    │
│ 网关/订阅池   │   │ 手机实测  │   │ 指纹比对  │   │ 去重排序  │
└─────────────┘   └──────────┘   └──────────┘   └──────────┘
                                                        ↓
                                                  ┌──────────┐
                                                  │ ⑤ 上传    │
                                                  │ GitHub   │
                                                  └──────────┘
```

### ① 找源

```bash
python tools/find_gateway.py          # 扫网关池，找活的 newlive 网关
python tools/scan_pool.py             # 扫订阅池
python tools/enum_hls.py              # 枚举某网关的 hls/N 编号
python tools/ip_owner.py              # 查 IP 归属（判断运营商/省份）
```

网关来源：`config/gateway_pool.txt`、`config/extra_hubei.txt`、`config/extra_gateway2.txt`
订阅来源：`config/subscribe.txt`、`config/subscribe_pool.txt`
黑名单：`config/blacklist.txt`、`config/url_blacklist.txt`

### ② 测速

**必须用目标设备测，不能用本机**（§4）。

```bash
python tools/phone_speed.py           # 生成手机端测速页/任务
python tools/local_speedtest.py       # 本机测速（仅参考，不排序）
python tools/speed_multi.py           # 多轮测速
```

手机端多轮结果用 `tools/phone_merge.py` 合并——**不要**用 `apply_phone_speed.py` 分批跑，
它一次只吃一组 list/result，分批会把未送测的线路误判成死链。

```bash
python tools/phone_merge.py           # 合并多轮手机结果
```

### ③ 判活（关键步骤，不可跳过）

```bash
python tools/audit_live.py output/curated.txt --wait 14 --workers 24
```

输出三类：`live` / `frozen` / `dead`。

### ④ 合并

```bash
python tools/merge_tv.py              # 主合并：去重 + 排序
python tools/fix_by_audit.py --apply  # 按审计结果删冻结快照
python tools/purge_dead.py            # 清死链
python tools/fill_missing.py          # 补缺口频道
python tools/reorder_by_phone.py      # 按手机实测速率重排
```

排序原则：

1. 可用（HTTP 200 且 >100KB）优先
2. Mbps 降序
3. 原始顺序兜底

每个频道保留 **3 条**冗余（多网关），第一条是首选。

### ⑤ 上传

```bash
cp config/publish.example.json config/publish.json   # 首次：填自己的账号
echo "你的 PAT" > tools/token.txt                    # 首次：写 token
python tools/gh_api.py push output/curated.txt
```

`tools/gh_api.py` 的通道选择逻辑：

```python
PROXY = os.environ.get("GITHUB_PROXY", "")   # 空=自动；填 none=强制直连
LOCAL_PROXY = "http://127.0.0.1:7897"

def _candidates():
    if PROXY.lower() in ("none", "direct", "0"):
        return [None]
    if PROXY:
        return [PROXY]
    if _port_open("127.0.0.1", 7897):
        return [LOCAL_PROXY, None]
    return [None]
```

**推送失败先怀疑代理，不要急着判断"链路被封"。** 我犯过这个错：
直连 301/406/404、7897 `SSL: UNEXPECTED_EOF_WHILE_READING`、57512 `Tunnel 502`，
三条全挂后我判定链路被干扰——实际只是瞬时抖动，换成系统代理 `127.0.0.1:7897` 重试即通。

Windows / Git Bash 两个坑：

```bash
export MSYS_NO_PATHCONV=1                    # 否则 /user 被转成 C:/Program Files/.../user
export https_proxy=http://127.0.0.1:7897 http_proxy=http://127.0.0.1:7897
```

## 8. 故障排查

| 症状 | 排查方向 |
| --- | --- |
| 测速很快但播不出 | **冻结快照**，跑 `audit_live.py` 看 MEDIA-SEQUENCE 是否增长（§1） |
| 台标对不上频道名 | 编号体系混用，抓帧或读 SDT 确认（§2） |
| 本机全超时但手机正常 | 出口运营商不同，**不要降权**（§4） |
| 推送报 `URL can't contain control characters` | `export MSYS_NO_PATHCONV=1` |
| 推送 SSL/502/404 全挂 | 换系统代理重试，别判定"被封"（§5） |
| ffprobe/ffmpeg `WinError 2` | 不在 PATH，用绝对路径 |
| ffmpeg 拼图不出文件 | 单帧输出加 `-update 1` |
| 台标拼图糊 | 单格提到 640×360 以上（§2） |
| 分批手机测速把好源判死 | 用 `phone_merge.py` 合并，别用 `apply_phone_speed.py` 分批 |

## 9. 待办 / 已知风险

- **7 个单线台**（无冗余，任一条挂掉即失台）：
  CCTV-16、内蒙古、新疆、江西、西藏、广州综合、海南
- **119.125.131.239 整机失效**：33 条已沉底保留，待观察是否恢复
- 斐讯 T1 实机验证央视频TV APK 的 32 位 ABI 兼容性——需 `adb connect <ip>:5555`
- 省内网关晚高峰掉速（白天快、晚上几十 k）是运营商 QoS，非源问题，
  只能靠**多网关冗余**对冲，找新网关的维护成本过高，不划算
